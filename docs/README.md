# 문서 전략

이 디렉터리는 Philosophers의 구조와 동작 계약을 설명하고, AI가 그 계약으로부터 코드를 구현·수정할 때 참조하는 기준이다. 문서는 한국어로 작성하며 코드 식별자는 원문을 유지한다.

## 읽는 순서

1. 루트 [AGENTS.md](../AGENTS.md)의 작업 규칙을 읽는다.
2. [Container 개요](containers/README.md)로 시스템 경계를 파악한다.
3. [실행 프로그램](containers/philo.md)에서 책임, 상태, 동기화 계약을 확인한다.
4. [핵심 흐름 목록](flows/README.md)에서 구현할 기능과 실패 경로를 선택한다.
5. 해당 흐름과 연결된 코드를 읽고 구현·검증한다.

## 디렉터리와 C4 수준

| 위치 | 역할 |
| --- | --- |
| `containers/` | C4 System Context(L1), Container(L2), 필요한 내부 Component(L3)와 코드 매핑 |
| `flows/` | 핵심 기능의 트리거, 순서, Container 및 내부 Component 간 상호작용, 실패·종료 조건 |
| `templates/` | AI와 사람이 새 문서를 작성할 때 사용하는 공통 형식 |

C4의 Container는 독립 실행·배포 단위다. 이 프로젝트의 Container는 `philo` 실행 프로세스 하나다. C 파일, pthread, mutex는 Container가 아니다. 따라서 흐름에서는 단일 Container 내부 Component 간 호출과 POSIX 런타임 상호작용을 함께 설명한다. POSIX는 실행 기반이며 별도 애플리케이션 Container로 세지 않는다.

## 사실과 설계의 구분

문서 상태는 `현재 구현`, `부분 구현`, `설계` 중 하나로 표시한다. 부분 구현 문서는 동작별로 구현된 부분과 미구현 계약을 구분한다. `설계`는 구현 목표이지 실행 검증 결과가 아니다. 코드 위치와 함수가 존재하더라도 정상 빌드나 동작을 보장하지 않는다.

초기 문서는 작업 트리의 코드를 기준으로 작성했다. 현재 `run_simulation`은 빈 구현이고 `philo_routine`은 없으며, 헤더의 미정의 `t_info`, `ptread_mutex_unlock` 오타, 미정의 변수·선언 등 빌드 장애가 있다. Makefile과 테스트도 아직 없다. 기존 `계획.md`는 작업 메모이며 구현 계약을 대신하지 않는다.

## 유지보수

- 안정적인 ID(`C-PHILO`, `CMP-*`, `F-*`)로 문서·다이어그램·코드를 연결한다.
- 구조·상태 소유권은 Container 문서, 동작 순서와 예외는 Flow 문서에 둔다. 중복 설명 대신 상대 링크를 사용한다.
- 변경할 계약을 먼저 문서화하고 코드를 구현한 뒤 실제 결과에 맞게 상태와 검증 기록을 갱신한다.
- 코드와 문서가 다르면 어느 쪽이 현재 사실인지 기록하고, 사용자 요구와 명시된 설계 계약을 기준으로 해결한다. 미구현 설계를 구현 완료로 표시하지 않는다.
- 새 문서는 [Container 템플릿](templates/container.md)과 [Flow 템플릿](templates/flow.md)을 따른다. 비해당 항목은 이유와 함께 `해당 없음`으로 남긴다.
- 다이어그램은 Mermaid를 사용한다. 다이어그램 ID와 본문의 이름을 일치시키고, 문서 간 상대 링크를 유지한다.
