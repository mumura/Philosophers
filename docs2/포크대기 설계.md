# 관리자 시간 안내 · 상세 계약

- 상태: 부분 구현. `adaptive` 적용 완료. 생각 시간의 현재 계약·코드 매핑은 [adaptive](adaptive.md) 참조. 1~3단계 공통 계약·목표 종료 보완 적용. C/D의 과거 실험 기록과 현재 adaptive 적용 상태를 구분. [개요와 구현 범위](설계.md)를 먼저 확인.
- 아래 A는 확정 계약, B는 현재 코드 비교, C는 보류 설계, D는 검증 기준.
- C/D는 과거 보류·실험 이력을 포함. 현재 적용 상태는 [adaptive](adaptive.md)가 우선하며, 나머지 미채택 후보를 완료로 간주하지 않음.

## A. 확정 계약

### 1. 책임과 실행 위치

| 구성 | 책임 | 실행 위치 |
|---|---|---|
| 철학자 | 관리자 호출, 안내받은 시간만큼 `usleep`, 실제 포크 획득·반환, 행동 결과 보고 | 철학자별 worker |
| 관리자 함수 | 실제 기록 갱신, 후보 유지·재선정, 행동 완료·진행 중단 판단, 대기 시간 계산 | 호출한 worker. 별도 시간 배정 스레드 없음 |
| 모니터 | 최신 후보로 사망 확정·출력, 전체 식사 목표 판정·종료 확정 | 메인 스레드 |
| 자원 관리 | 초기화·부분 실패 정리·실행 후 역순 정리 | 기존 `with_resource()` 재귀 흐름 |

- 철학자는 다른 철학자와 소통하거나 이웃의 상태를 해석해 시간을 계산하지 않음.
- 행동 시작 전·각 기상 후 관리자 함수를 호출. 포크 확보·식사 완료·반환 등 실제 결과도 함수로 보고.
- 관리자는 호출 시 실행 종료·만료 여부와 현재 행동 완료 여부를 확인. 계속 진행할 수 있고 미완료이면 대기 시간 안내.
- 관리자 함수가 만료를 발견하면 해당 행동의 진행을 중단시키고 기록을 보존. worker가 직접 사망을 확정·출력하거나 그 기록을 새 식사로 갱신하지 않음. 메인 모니터가 최신 상태로 사망 확정.
- 반환 형식은 구현안에서 결정. 정상 행동 완료와 전체 실행 중단은 구분 가능해야 하며, 추가 대기를 별도 상태값으로 만들지는 않아도 됨.

### 2. 행동과 보고 순서

1. 공통 시작 동기화·기존 시작 시차 이후 관리자가 초기 생각 시간을 배정. 완료 후 기존 획득 순서로 양쪽 포크 확보.
2. 두 포크 확보를 관리자에 보고. 관리자가 실행·자기 만료 여부 확인 후 식사 시작 시각과 기록 갱신.
3. 식사 로그 출력 후 공통 대기 반복. 기록 시각부터 계산한 식사 종료 시각 유지.
4. 정상 식사 완료 시 완료 보고·횟수 반영. 중단이면 정상 완료로 세지 않음.
5. 실제 포크 반환·상태 보고 후 수면 시작. 관리자에게서 수면 대기 시간을 받아 공통 반복 수행.
6. 생각 로그 후 관리자가 adaptive 계산·대기·점유 재확인. 완료 후 다음 포크 획득으로 반복.

- 요청 등록·예약·식사 허가 단계는 이 확정 흐름에 추가하지 않음.
- 기존 시작 시차는 유지. 생각 시간은 사용자 승인으로 [adaptive](adaptive.md)를 적용. 기존 예측/양보는 주기 계산 불가 시 후퇴 경로로 유지.
- 포크 획득 순서로 순환 대기를 예방하는 기존 정책 유지. 관리자 상태 잠금을 보유한 채 실제 포크 획득·대기 금지.
- 1명일 때 같은 포크 뮤텍스를 두 번 획득하지 않음. 단일 포크 보유·사망 감시·정지 시 반환 경로 유지.
- 관리자 문의는 실제 포크 뮤텍스의 획득 성공을 보장하지 않으며, 블로킹 포크 대기를 즉시 중단시키는 기능도 아님.

### 3. 시간 기준과 공통 대기

- 식사 시작은 실제 두 포크 확보 후 관리자가 기록한 시각. `식사 종료 시각 = 식사 시작 시각 + time_to_eat`.
- 수면도 관리자 호출에서 시작 시각을 한 번 정해 `수면 종료 시각 = 수면 시작 시각 + time_to_sleep`으로 유지.
- 관리자가 원래 행동 종료 시각을 보존. 로그 처리·중간 기상·재문의 후 현재 시각에 행동 시간을 다시 더하지 않음.
- 모든 계산은 같은 시간 기준 사용. 식사·수면 입력 시간을 임의로 단축하지 않음.

```text
행동 시작 시 관리자에서 종료 시각을 한 번 정함
반복:
    관리자 함수 호출
    실행 중단·만료 여부 확인
    중단해야 하면 행동을 멈추고 보유 포크 반환 경로로 진행
    정상 행동 종료 시각에 도달했으면 정상 완료
    그 외에는 다음 대기 시간을 안내
    관리 잠금을 보유하지 않고 usleep(할당 시간)
    기상 후 반복 처음으로 돌아가 재문의
```

- 행동 남은 시간 = 원래 행동 종료 시각 − 현재 시각.
- 사망 확인까지 남은 시간 = 현재 감시 후보의 `last_meal + time_to_die` − 현재 시각.
- 두 값이 양수이면 기본 할당 시간은 최솟값. 목표 종료 보완이 활성화되기 전에는 행동이 먼저 끝나면 끝까지 대기하고, 사망 확인이 먼저이면 그 시각에 기상해 재문의.
- 사망 시각 직전 기상을 위한 별도 여유는 두지 않음. 실제 기상에는 실행 지연이 있을 수 있음.
- 사망 확인 시각 전에 후보가 갱신돼도 매번 깨우지 않음. 이미 안내한 시각에 기상해 최신 후보로 재계산.
- 조기 기상·늦은 기상은 실제 현재 시각으로 처리. 할당한 `usleep` 시간을 누적해 경과 시간으로 간주하지 않음.
- 중간 기상은 행동 완료가 아님. 정상 식사 횟수 반영·다음 행동 진입 없이 남은 시간을 다시 안내.
- 후보가 실제 만료됐으면 음수 대기·0ms 재문의 반복을 만들지 않고 A.1의 진행 중단·모니터 판정 경로로 연결.
- 사망 시각에 맞춘 분할은 긴 대기로 인한 종료·회수 지연 축소 목적. 기아 방지와 별개.
- 위 시간식은 종료 시각이 정해진 대기의 공통 계약. 보류된 엇박 예측·예약 대기에 대한 새 종료 조건을 정하는 것은 아님.

#### 목표 종료 대비 대기 전환

- `finish_meal()`은 정상 식사 완료 후 목표 횟수에 처음 도달한 철학자만 `full_count`에 한 번 반영. 완료 전에 미리 올리지 않음.
- 관리자가 상태 잠금 안에서 `full_count > 0`을 확인하면 새 대기 할당을 최대 10ms로 제한. 행동·사망 확인까지 더 짧게 남았으면 그 짧은 값 사용.
- 첫 목표 완료 전에는 기존 대기 정책 유지. 목표 횟수가 없으면 `full_count`가 증가하지 않으므로 이 전환도 없음.
- 별도 플래그·예약·요청 큐 없이 기존 완료 인원 사용. 모두 완료하기 전 정상 행동·완료 횟수 집계는 기존대로 유지.
- 전환 전에 길게 잠든 미완료 worker는 자신의 목표를 채워야 전체 목표 달성이 가능. 목표를 채운 뒤 새 대기에 들어가면 이미 전환된 정책을 적용받음.
- 전환은 이미 진행 중인 `usleep`을 깨우는 동작이 아님. 짧아진 할당도 원래 행동 종료 시각을 바꾸거나 완료로 처리하지 않음.
- 목적은 전체 목표 달성 후 종료 관측·반환 지연 축소. 스케줄링·포크 잠금 대기를 포함한 실제 종료의 엄격한 10ms 상한은 아님.
- 첫 완료자가 나와도 다른 철학자가 오래 남아 있을 수 있으며, `must_eat=1`이면 빠르게 전환됨. CPU 비용·종료 지연을 함께 측정해 평가.


### 4. 식사 기록과 감시 후보

- 철학자 배열에 최신 `last_meal`을 유지하고 덮어씀. 관리자에 최장 미갱신 후보의 인덱스 또는 포인터 하나 보관.
- 시작 시 모든 `last_meal`을 공통 시작 시각으로 설정하고 후보 선정. 동률이면 번호가 작은 후보 선택.
- 식사 시작 보고 처리 시, 상태 잠금 안에서 실행·자기 만료 확인 → 현재 식사 시각 기록 → 필요한 후보 재선정을 함께 수행.
- 갱신한 철학자가 후보가 아니면 후보 유지. 현재 후보가 갱신되면 전체 최신 `last_meal`을 한 번 순회해 새 최솟값 후보 선정.
- 모니터의 평소 사망 검사와 관리자의 대기 기준 조회는 저장된 후보 사용. 후보를 확인하는 매번 전체를 순회하지 않음.
- 식사마다 노드 할당·해제하지 않음. 누적 기록 큐·옛 기록·`version`에 의한 무효 기록 제거는 목표 사망 감시에서 사용하지 않음.
- 전제: 공통 `time_to_die`, 각 식사 시각의 비감소. 시각 역행·시각 획득 오류는 구현안에서 실패 정책을 명시하고 정상 식사 갱신으로 취급하지 않음.
- 불변 조건: 상태 잠금 밖에 공개되는 후보의 `last_meal`은 전체 최솟값. 기록 갱신·후보 재선정·사망 검사는 같은 상태 잠금으로 보호.
- 평소 확인·비후보 갱신 O(1), 후보 갱신 시 O(N). 최악에는 재선정이 매 식사마다 발생할 수 있음.
- 감시 후보는 사망·대기 기준이며, 식사 순서나 포크 예약 우선순위가 아님.

### 5. 상태와 출력의 잠금

| 작업 | 순서 |
|---|---|
| 기록·후보 갱신 | 상태 잠금 → 확인·갱신 → 상태 잠금 해제 |
| 일반 로그 | 출력 잠금 → 상태 잠금 → 실행 상태·출력 정보 확인 → 상태 잠금 해제 → 허용된 경우 출력 → 출력 잠금 해제 |
| 사망 확정·로그 | 출력 잠금 → 상태 잠금 → 현재 시각·최신 후보로 사망 재확인·전체 종료 확정 → 상태 잠금 해제 → 사망 출력 → 출력 잠금 해제 |

- 상태 잠금을 보유한 채 출력 잠금을 기다리는 경로 금지. 상태 갱신 함수에서 바로 출력하지 않음.
- 사망 재확인 결과 만료되지 않았다면 사망 출력하지 않음. 잠금 획득 전에 복사한 오래된 후보만으로 확정하지 않음.
- 사망 로그는 한 번만 출력하고 이후 일반 로그 차단. 일반 로그와 사망 로그의 출력 순서는 출력 잠금으로 직렬화.
- 출력 중 상태 잠금은 보유하지 않음. 출력 지연 자체나 출력 잠금을 기다리는 worker의 지연까지 없애는 것은 아님.
- 실제 포크 획득·`usleep`·`join` 중 상태 잠금을 보유하지 않음.
- `stop`은 기존 의미 유지: 1=실행, 0=정지. 모든 공유 읽기·쓰기는 상태 잠금으로 보호.

### 6. 종료와 재귀 자원 관리

- 사망 경계는 `현재 시각 - 후보 last_meal >= time_to_die`. 만료된 기록을 새 식사 갱신으로 되살리지 않음.
- 모니터가 동일 시점의 사망 조건을 먼저 확인한 뒤 전체 식사 목표 확인. 둘 다 충족되면 사망 우선.
- 이미 목표 달성으로 정상 종료됐으면 미래 사망을 기다리거나 종료 사유를 뒤집지 않음.
- 전체 목표는 정상 식사 완료 횟수에 따라 집계. 중간 기상·중단된 식사를 완료로 세지 않음.
- 종료 시 보유 포크를 반환하고 worker의 공유 자원 접근 종료를 확인. 실제 생성된 스레드만 회수.
- `with_resource()`의 재귀 초기화·반환 시 역순 정리 유지. 시간·감시 변경을 이유로 별도의 자원 해제 흐름을 만들지 않음.
- 초기화 실패는 해당 단계의 부분 자원을 정리하고 이전 성공 단계는 재귀 반환으로 정리. 스레드 부분 생성 실패는 생성된 worker 정지·회수 후 정리.
- `released`만으로 `pthread_join` 성공을 간주하지 않음. 기존 실패 경로를 보존하고 변경이 필요하면 구현안에서 별도 설명.

## B. 현재 구현과의 차이

- 아래는 문서 정리 시 확인한 코드 사실. 구현 착수 때 실제 파일·호출부를 다시 대조.

| 항목 | 현재 코드 | 확정 계약에 따른 변경 |
|---|---|---|
| 식사 기록 · 1단계 적용 | `monitor/meal_deadline.c:update_meal_locked()`에서 기록 덮어쓰기·후보일 때만 재선정. 초기 후보는 `start_philos()`, 감시는 `state.oldest` 사용 | 적용 완료. 기록 큐·감시용 `version`·큐 초기화/정리 제거 |
| 시간 기준 · 2단계 적용 | `record_meal_start(p, &end)`가 식사 시작과 함께 종료 시각 확정. 수면은 로그 전에 `get_action_end()`로 종료 시각 확정 | 적용 완료. `wait_until()`에 고정 종료 시각 전달 |
| 대기 반복 · 2단계 적용 | `base/wait.c`의 `wait_until()`이 상태 잠금 아래 후보·현재 시각으로 다음 대기 계산, 잠금 해제 후 `usleep` | 후보 만료면 중단 반환. 전체 `stop` 변경·사망 출력은 모니터 유지 |
| 목표 종료 대비 · 적용 | `action_wait_locked()`가 `full_count > 0`이면 새 할당을 최대 10ms로 제한 | 완료 전 긴 대기 정책과 원래 행동 종료 시각 유지. 전체 목표 판정은 모니터 유지 |
| 생각 단계 · adaptive 적용 | 초기/후속 `manager_thinking()`으로 배정·대기·점유 재확인 | [현재 계약](adaptive.md) 참조. 예약·차례 강제 없음 |

## C. 보류 설계 · 구현 대상 아님

### 1. 포크 시간 배열과 엇박 유도

- 목적: 관리자가 양옆 식사 시각으로 포크가 풀릴 즈음 돌아오도록 대기를 안내해 획득 시도의 리듬 조절·불필요한 대기 축소.
- `fork_state`·`get_think_delay()`는 현재 코드에 존재. 유지·변경·제거, 예상 반납 계산식, 예측 불가 상태의 재문의 간격은 후속 논의.
- 배열이 기아의 직접 원인이거나 CPU 개선에 무효라고 단정하지 않음.
- 시간 기준·기상 후 재문의와 연결되지만, A의 공통 계약만으로 새 배열 정책을 정하지 않음.

#### 실험안 · 여유에 따른 제한적 생각 대기

- 상태: 아래 초기 규칙을 `/tmp` 복사본에서 구현·비교한 탐색 실험. 프로젝트 코드에는 미채택. A의 확정 계약을 바꾸거나 추가 구현을 승인하는 근거로 사용하지 않음.
- 주목적: 포크 획득 대기와 한 포크를 보유한 채 다른 포크를 기다리는 시간 축소. 엇박은 이를 위한 수단.
- 정책: 관리자가 자신보다 급하고 획득을 기다리는 이웃을 확인하면, 여유 있는 쪽의 생각 시간만 제한적으로 늘림.
- 철학자는 배정된 시간만큼 대기·행동. 이웃의 상태·우선순위·양보 이유를 전달받거나 스스로 판단하지 않음.
- 강제 식사 순서·요청 큐·포크 예약·허가는 이 실험에 도입하지 않음. 진행 중인 식사·수면을 단축하거나 이미 잠든 철학자의 대기를 바꾸지 않음.

| 계산 자료 | 후보 정의·용도 |
|---|---|
| 내 남은 여유 | `내 last_meal + time_to_die - 현재 시각` |
| 이웃 남은 여유 | `이웃 last_meal + time_to_die - 현재 시각`. 작은 쪽을 더 급한 것으로 비교 |
| 실제 포크 상태·식사 시작 시각 | 이웃 식사 중이면 기존 예상 반납 시간을 참고하되, 실제 반환을 보장하는 값으로 취급하지 않음 |
| 이웃의 현재 행동 상태 | 수면 중인지, 식사하려고 포크 획득을 기다리는지 구분. 오래된 `last_meal`만으로 대기 중이라고 판단하지 않음 |

- 관리자 판단 후보: 이웃 식사 중이면 예상 반납 참고 → 더 급한 이웃이 획득 대기 중이고 내 여유가 있으면 짧은 생각 대기 추가 → 기상 후 실제 상태로 재계산.
- 내 여유가 부족하면 추가 양보 대기는 하지 않음. 내 사망까지 남은 시간을 전부 양보 시간으로 쓰지 않으며, 이후 포크 획득에 필요한 여유를 남기는 규칙이 필요.
- 짧은 재확인 간격·최대 양보 한도를 실험 매개변수로 둠. 구체적인 값·누적 한도·동률 처리·획득 여유의 계산법은 아직 미결정.
- 반복 재계산이 매번 양보 한도를 새로 시작해 무한히 미루지 않도록, 한 생각 단계의 전체 양보 범위를 함께 검토.
- 현재 포크별 소유자·식사 시작 시각만으로는 이웃의 수면과 획득 대기를 충분히 구분할 수 없음. 관리자 측 행동 상태의 저장·보고 방법은 실험 구현안에서 제시.
- 이미 배정한 시간은 참고하더라도 기존 배정을 다시 쓰거나 전체 일정을 재편하지 않음. 이를 이번 계산에 포함할지와 필요한 저장 방식은 미결정.
- 효과의 한계: 포크 획득을 강제하지 않으므로 엄격한 기아 방지·식사 순서·항상 생존을 보장하지 않음.
- 과제 적합성: 판단을 관리자 안에 숨긴다는 사실만으로 통신 금지 조건 충족을 확정하지 않음. 이웃 상태 이용 범위는 명세·평가 기준과 별도로 대조.
- 비교: 같은 획득 순서에서 추가 생각 대기 없음 / 기존 반납 예측 / 제한적 양보 실험을 구분. 다른 감시·잠금 변경은 동일하게 유지.
- 지표: CPU 시간·기상 횟수·첫 포크 보유 후 두 번째 획득까지 시간·생각 시간을 포함한 최대 식사 시작 간격·사망 여부·목표 식사 횟수 달성.
- 포크 대기만 생각 대기로 옮긴 결과를 성능 개선으로 간주하지 않음. 반복 실행에서 기아·총 식사 지연·CPU 비용이 악화되면 계산법을 재검토하거나 실험을 중단.

### 2. 공정한 요청과 두 포크 예약

- 원칙: 늦은 충돌 요청이 먼저 기다린 요청을 반복 추월하지 못하게 함.
- 선행 요청의 한쪽 포크가 사용 중이어도 뒤의 충돌 요청이 필요한 포크를 먼저 가져가지 못하도록 우선권 보호.
- 이미 진행 중인 식사는 유지하고, 실제 두 포크 반환 확인 후 관리자가 함께 예약·허가. 실제 뮤텍스는 철학자가 획득·반환.
- 허가 전에는 포크를 하나 잡고 기다리지 않음. 필요한 포크가 겹치지 않는 요청은 동시 허가 가능.
- 재문의해도 요청 순서 유지. 실제 식사 기록은 허가 시점이 아니라 실제 두 포크 확보 후 갱신.
- 요청 등록·번호·저장 방식, 허가 후 오류, 취소·반환·1명 처리 세부사항은 미결정.
- 별도 요청 큐는 필수가 아님. 관리자 측 철학자별 대기 상태·요청 번호로도 표현 가능하며 감시 후보와는 별도 자료.
- 공정성은 진행 가능한 스레드와 유한한 식사·반환을 전제. 모든 입력의 생존이나 최대 동시 식사를 보장하지 않음.
- 이 원칙은 A의 확정 실행 흐름에 아직 적용하지 않음.

### 2단계 검증 기록 · 2026-11-06

- 적용: `base/wait.c` 추가. 관리자 계산은 `action_wait_locked()`, 대기 반복은 `wait_until()`. `wait_ms()`는 기존 호출을 위한 상대 시간 래퍼로 유지.
- 식사 시작 기록과 동시에 종료 시각을 출력 인자로 반환. 식사·수면 로그 처리 뒤에 전체 시간을 다시 더하지 않음.
- 구현 제한: `usleep` 인자를 1초 미만으로 유지하기 위해 한 번의 할당은 최대 999ms. 그보다 이른 행동 종료·후보 사망 시각이 있으면 해당 시각까지 대기.
- 후보 만료는 worker의 행동 중단·포크 반환으로 연결하지만 `stop=0`이나 사망 출력은 하지 않음. 모니터가 기존 경로에서 확정. 시각 획득 실패·행동 종료 시각 덧셈 범위 초과는 오류로 중단.
- 기존 포크 획득·엇박 계산·worker 반복·후보 재선정·모니터 우선순위/최대 10ms 확인·재귀 자원 관리는 변경 전 해시와 비교해 유지 확인.
- 빌드·변경 파일 Norminette·차이 공백 검사 통과.
- 임시 가짜 시계 검증: 로그 처리 시간이 식사·수면에 추가되지 않음, 조기/지연 기상, 대기 중 후보 갱신, 정확한 만료 경계, 식사 중단 시 횟수 미증가·포크 반환, 대기 중 상태 잠금 해제, 999ms 분할, 정지·시각 오류·범위 초과 확인.
- 실제 실행: `2 800 100 100 5`, `4 1000 100 100 5`, `5 3000 50 50 5` 목표 종료 확인. `1 200 100 100`, `4 150 100 100`, `2 250 50 1000` 사망 종료·사망 이후 일반 로그 없음 확인.
- `5 800 200 200 10`, `3 610 200 200 5` 사망 재현. 기아 해결을 주장하지 않음.
- Valgrind: `4 3000 30 30 3` 목표 종료·`1 100 30 30` 사망 종료에서 누수·메모리 오류 0. Helgrind: `4 3000 30 30 3`에서 보고된 오류 0. 실행한 조건의 검증이며 전체 경쟁 부재 증명은 아님.
